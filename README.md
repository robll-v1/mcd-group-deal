# 🍔 麦凑单 · mcd-group-deal

> 一群人点麦当劳时，帮你把满减吃满、把账分清楚。
> 基于 [麦当劳中国 MCP](https://github.com/M-China/mcd-mcp-server) 的 WorkBuddy Skill。

**核心命题：吃饭凑单这道算术题，人算不清，大模型也算不清。**

---

## 它到底解决什么

场景很日常：办公室 4 个人一起点麦当劳，各点各的加起来 ¥119.50。

满减阶梯长这样：

| 门槛 | 减 |
|---|---:|
| 满 90 | 18 |
| 满 100 | 25 |
| 满 120 | 40 |
| 满 150 | 60 |

¥119.50 → 只能用满 100 减 25 → **实付 ¥94.50**。

麦凑单会告诉你：

> **再加一份 ¥6.00 的甜筒，订单推到 ¥125.50，用满 120 减 40，实付 ¥85.50。**
> 多花了 6 块，反而少付 9 块。

这是真枚举出来的，不是估算。人类嫌烦不会去算，大模型心算基本会错——但它只需要被算一次。

然后它还负责下一件更烦的事：**这 4 个人各该付多少**。

## 实际输出

跑 `python3 scripts/demo.py`（离线，不需要 Token）：

```
【第一次算】各点各的：原价 ¥119.50，优惠 ¥25.00，实付 ¥94.50
【最优解】再加一份「甜筒」(6.00元) 把订单推到满 120.00 减 40.00，实付反而少 9.00 元
```

生成的**分账卡**（可直接截图发群）：

| 人 | 点单 | 小计 | 分摊优惠 | 应付 |
|---|---|---:|---:|---:|
| 张伟 | 巨无霸、可口可乐（中）、甜筒（公摊） | ¥36.50 | -¥11.63 | **¥24.87** |
| 李娜 | 麦辣鸡腿堡、中薯条、甜筒（公摊） | ¥36.00 | -¥11.47 | **¥24.53** |
| 王强 | 板烧鸡腿堡、零度可乐（中）、甜筒（公摊） | ¥35.00 | -¥11.16 | **¥23.84** |
| 赵敏 | 麦香鱼、甜筒（公摊） | ¥18.00 | -¥5.74 | **¥12.26** |
| **合计** | | ¥125.50 | -¥40.00 | **¥85.50** |

每人分摊的优惠加起来，**和实付金额一分不差**。

> AA 分账最常见的翻车就是「每人算完加起来差一毛钱」——整数分 + 最大余数法可以彻底消除它。
> 见 `scripts/test_optimizer.py` 里的 `test_allocate_exact`。

## 快速开始

### 1. 申请 MCP Token

去 [open.mcd.cn/mcp](https://open.mcd.cn/mcp) 用手机号登录 → 控制台 → 激活 → 复制 Token。免费。

### 2. 配置连接器

把 `mcp-config.example.json` 的内容填进 WorkBuddy 的
**连接器 → 自定义连接器 → 配置 MCP**，并把 `${MCD_MCP_TOKEN}` 换成真实 Token：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamable-http",
      "url": "https://mcp.mcd.cn",
      "headers": { "Authorization": "Bearer 你的_TOKEN" }
    }
  }
}
```

> ⚠️ `Authorization` 必须带 `Bearer ` 前缀，裸 token 会被服务端以 403 拒绝。
> 保存后回到「自定义连接器」把 `mcd-mcp` 启用。

### 3. 直接用

```
我们办公室 4 个人一起点麦当劳，我、张伟、李娜、王强，
预算都 40 以内，送到陆家嘴，怎么点最便宜？谁该付多少？
```

### 4. 只想离线看看效果（不需要 Token）

```bash
python3 scripts/demo.py            # 完整演示 + 分账卡
python3 scripts/test_optimizer.py  # 引擎自测，6/6 通过
```

无第三方依赖，Python 3.9+ 标准库即可。

## 它是怎么工作的

```
MCP 负责「事实」                   本地引擎负责「算术」
─────────────────                ─────────────────
门店 / 菜单 / 价格 / 券    ──→    组合枚举 · 门槛求解 · 分摊进位
        ↓                                  ↓
   create-order  ←────────────  分账卡 + 用户确认
```

刻意把两件事分开：**让模型算钱，是这类项目最容易翻车的地方。**

引擎搜索三条确定性路径：

| 路径 | 做什么 | 例子 |
|---|---|---|
| **凑门槛** | 算出「补多少 → 换多少减免 → 净收益是否为正」 | 加 ¥6 甜筒，省 ¥9 |
| **拆单** | 一单用大额满减 vs 拆两单各用一张券，取实付更低 | 两组各满 90 减 18 |
| **换品** | 同品类换更便宜的，且不跌出门槛 | 大薯换中薯 |

金额全程用**分**为单位的整数运算，不碰浮点。

## 为什么不是「又一个点餐助手」

| 常见做法 | 麦凑单 |
|---|---|
| 让模型读菜单，凭感觉推荐 | 穷举方案的实付价，取最低 |
| 「帮你下单」就结束了 | 先给分账卡，确认后才下单 |
| 优惠按人头平分 | 按各自金额比例分摊，一分不差 |
| 只管一个人 | 从第一天就按团餐设计（`beType=6`）|

还有一条边界我很在意：**它永远不替你付钱。**
麦当劳 MCP 没有支付能力，`create-order` 只产待支付订单。
所以刻意不做「全自动下单」——**点单交给我，付钱永远留给你。**

## 已知限制

诚实地列出来，比藏着好：

1. **不能自动支付。** MCP 无支付工具，最后一步必须用户自己付。
2. **凑单搜索是启发式的。** 三条路径（加一件 / 拆两单 / 同品类替换）覆盖了绝大多数真实场景，
   但不是全局最优——真正的全局最优是带约束的整数规划，当前没做到那一步。
3. **一次只处理一件公摊补差品。** 需要连加两件才够门槛的情况暂未支持。
4. **示例数据不是真实价格。** `examples/sample-order.json` 里的菜单与价格均为虚构演示数据，
   真实运行时全部由 MCP 实时返回。
